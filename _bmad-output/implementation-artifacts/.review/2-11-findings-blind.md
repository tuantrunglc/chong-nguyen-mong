# Blind Hunter findings (Story 2.11)

## high — A stopped playback resumes and replays the old battle's log on the new board
- Where: game/src/battle/event_player.gd:54 (also 46-48, 59, 66-69); driven by game/src/battle/battle_view.gd:58-60
- Evidence: `func stop() -> void:` / `	_stopped = true` (66-69) vs `func play(...) -> void:` / `	_stopped = false` (54-56) and `func play_now(...)` / `	_stopped = false` (46-48); the only abort is the per-iteration `		if _stopped: return` (59).
- Why it fails: the "stopped" flag is one shared bool with no playback identity, and the next playback clears it. Sequence: enemy phase is animating (`_on_events_resolved` is suspended inside `_play_one`'s timer); player presses F5 → `_start_battle()` → `_battle_view.start()` runs `_player.stop()` (58-60) and bumps `_playback_generation`; `begin_battle()` → `_controller.begin()` → `_on_events_resolved` → `_player.play(events)` sets `_stopped = false` again (and if the prep log is empty, the `events.is_empty()` branch at battle_view.gd:195 calls `play_now`, which resets the flag at event_player.gd:48 just the same). The old coroutine's pending `SceneTreeTimer` then fires (≤ one event, ~0.3 s) and its `for` loop no longer sees `_stopped`, so it keeps playing the *previous* battle's remaining events on the new board: `_tween_to`/`_shake`/`_lunge` drive the new tokens' positions, `_sink_or_fade` sets `token.visible = false` on new units, and `_played` (already overwritten by the new call) no longer matches what is on screen. The comment at battle_view.gd:34 claims exactly this case is prevented ("lượt phát của trận cũ không được vẽ lên trận mới (F5 giữa lúc phát)"), but the generation is tracked only in the view, never inside the player.
- Fix: give each playback an id (`_play_id += 1` in `play`/`play_now`/`stop`) and have the loop bail when the id it started with is stale, instead of a shared `_stopped` bool.

## medium — `_finish_playback` clears the lock and the phase flag before checking that it still owns the battle
- Where: game/src/battle/battle_view.gd:203-209
- Evidence: `func _finish_playback(snapshot: BattleState, generation: int) -> void:` / `	_playing = false` / `	_enemy_turn = false` / `	if _controller == null or generation != _playback_generation:` / `		return`
- Why it fails: the stale-playback test happens *after* the two flags are mutated, so a coroutine belonging to a battle that no longer exists still writes the current battle's input lock. Sequence: playback of battle A is suspended; the screen is left (error/menu) or a new battle is started, so `stop()`/`start()` sets `_playing = false`; A's coroutine wakes, `play()` returns at its `_stopped` check, and `_finish_playback(old_snapshot, old_generation)` runs lines 204-205 unconditionally, then returns at 207. If battle B has meanwhile started its own playback (`_playing = true`, from battle_view.gd:191), the flag is now false while B's animation is still running: clicks/keys pass the guards at 118/132/172/179 and `_on_events_resolved` starts a second `_player.play()` on top of the still-suspended first one — two loops driving the same tokens, and B's own finish later clears a flag that belongs to whichever playback is running by then. The guard at 207 returns before the emit, so the board is not redrawn with the stale snapshot, but the lock state has already been corrupted.
- Fix: move the `_controller == null or generation != _playback_generation` check to the first statement of `_finish_playback`, before touching `_playing`/`_enemy_turn`.

## medium — the 3-second phase cap is only asserted on a helper nothing calls, and real playback can exceed it
- Where: game/src/battle/event_player.gd:38
- Evidence: `func total_seconds(events: Array[BattleEvent]) -> float:` / `	return minf(sum, MAX_PHASE_SECONDS)` (37-41) — `total_seconds` appears nowhere else in the patch except `game/tests/test_event_player.gd:50`: `assert_almost_eq(player.total_seconds(long_log), EventPlayer.MAX_PHASE_SECONDS, 0.001, ...)`; the real path is `play()` (54-64), which recomputes the sum itself in `_time_scale` (73-79) and then waits per event via `await _wait(...)` whose body is `await get_tree().create_timer(seconds).timeout` (197).
- Why it fails: `SceneTreeTimer` only resolves on a frame tick, so each event costs its scaled duration rounded *up* to the next frame. A busy phase (the case the cap exists for: many short events, e.g. 40 events × 0.075 s = 3.0 s) actually runs ≈ 40 frames longer than the arithmetic — ≈ 3.3-3.7 s at 60 fps — so NFR3's "one enemy phase ≤ 3 s" is exceeded. The test cannot catch this: it calls `total_seconds()`, which production never calls, so a regression where `play()` ignored `scale` entirely would still pass the cap test.
- Fix: drive each wait from a phase deadline (start + `MAX_PHASE_SECONDS`) minus elapsed time so rounding cannot accumulate, and assert the cap against a measured `play()` duration instead of the unused helper.

## low — Undo / End Turn are painted enabled during playback, then silently swallow the click
- Where: game/src/battle/battle_view.gd:320 (with 191-192, 317-323) and game/src/ui/hud.gd:63-64
- Evidence: `_playing = true` / `_update_hud()` (191-192) → `_hud.show_turn(snapshot.round_number, _controller.can_undo(), over)` (320) → `	_undo_button.disabled = over or not can_undo` / `	_end_turn_button.disabled = over` (hud.gd:63-64). `_playing` reaches neither `show_turn` nor `show_phase`.
- Why it fails: during the enemy phase of a fresh round `can_undo()` is true and `over` is false, so both buttons render enabled for the whole animation. Clicking End Turn (or pressing Space, or Z) hits the `_playing` guard at 172/179 and nothing happens; the player sees an accepted-looking control that is a no-op, and a second press right after playback ends submits immediately — the opposite of the "input locked" story the phase line is telling.
- Fix: include the locked state in the disabled computation (pass `_playing` into `show_turn`, or have the HUD take a `locked` flag set from `_on_events_resolved`).

## low — `_enemy_turn` is set by the caller and cleared only by a playback that actually runs
- Where: game/src/battle/battle_view.gd:101 and 181 (cleared only at 206)
- Evidence: `	_enemy_turn = true` then `	_controller.begin()` (101-102); `	_enemy_turn = true` then `	_controller.submit(Command.end_turn())` (181-182); the only reset in the file is `	_enemy_turn = false` in `_finish_playback` (206), and the phase line reads it at 323: `_hud.show_phase(_playing and _enemy_turn)`.
- Why it fails: the flag is raised before the command is submitted, but it is lowered only when a playback finishes. If `submit()`/`begin()` ever returns without emitting `events_resolved` (a rejected command, an empty no-op phase that does not emit), the flag is never cleared; the next playback — which may be the player's own attack — then satisfies `_playing and _enemy_turn` and the HUD says "Quân Nguyên đang ra đòn" while the player's unit lunges. (Whether the controller can return without emitting is outside this diff, so this is a structural defect rather than a demonstrated one.)
- Fix: set `_enemy_turn` from inside `_on_events_resolved` (e.g. a pending phase kind consumed there) instead of before the submit, so no emission means no leaked flag.

## low — hover is not locked during playback and reads the post-command state
- Where: game/src/battle/battle_view.gd:230 (with 242), against the other entry points at 118, 132, 172, 179
- Evidence: `func _on_cell_hovered(cell: Vector2i) -> void:` / `	_update_info(cell)` — no `_playing` guard, unlike every command entry point; `_update_info` starts with `	var state: BattleState = _controller.snapshot()` (242), i.e. the state *after* the command being animated.
- Why it fails: an enemy unit is animated from (3,3) to (5,3); while the token is mid-lunge the mouse sits over (3,3) — `unit_at((3,3))` is already empty, so the tooltip disappears although a token is visibly standing there; hovering (5,3) shows the unit's name/HP before its token has arrived, and the red "đòn sắp đánh" overlay painted from that state appears over a board that is still showing the previous positions. The final `_update_info` at 228 corrects it after playback, so this is a wrong-frame artefact, not a stuck state.
- Fix: ignore `cell_hovered` while `_playing` and let the existing refresh at 226-228 repaint the tooltip when playback finishes.

## Verified-clean areas
1. **No stuck coroutine / double resume.** Every suspension in the playback path goes through `_wait()` (event_player.gd:194-197), which awaits a `SceneTreeTimer`, never `Tween.finished` and never a signal `stop()` could cancel; `stop()` therefore cannot leave `_on_events_resolved` suspended, and each `events_resolved` emission drives exactly one coroutine, so `_playing` cannot be stranded true (a permanent input lock is not reachable from this patch).
2. **Command entry points are locked.** All four command paths got the `_playing` guard — general keys (118), cell clicks (132), undo (172), end turn (179) — and the HUD buttons route through those same handlers; the only unguarded entry point is hover, which cannot submit anything.
3. **Redraw ordering after playback.** `playback_finished.emit(snapshot)` (210) happens before `_deselect`/`_select` and before the hover/highlight recomputation (211-228), so `main.gd`'s `_show_board` still runs before the view recomputes `_cells` and the telegraph highlight — the old "connect main before BattleView" ordering is preserved.
4. **Event deltas are positional, not state-based.** `_delta` (140-141) is added to the token's *current* position (`token.position + _delta(event)`, 106) instead of `token.cell`, so several MOVED events for one unit in one log compose correctly, the fortress-cell lift is preserved, and lunge/shake return to their start.
